## 1. 미니피드 분석 요약

### 1.1 저장소 파일

| 파일 | 역할 |
| --- | --- |
| `CONTRIBUTING.md` | 규칙의 본체. 환경 세팅, 작업 흐름, 브랜치·커밋·PR 형식, 리뷰, 머지 조건, 금지 사항 |
| `.github/ISSUE_TEMPLATE/feature.yml` · `bug.yml` · `task.yml` | 이슈 양식 3종. 빈 이슈 금지 |
| `.github/ISSUE_TEMPLATE/config.yml` | 이슈 만들 때 명세서·테스트 케이스·전체 일정 링크를 띄움 |
| `.github/pull_request_template.md` | 관련 이슈, 작업 내용, 검증 결과, 스크린샷, AI 기록, 리뷰 포인트, 체크리스트 |
| `.github/workflows/ci.yml` | main 대상 PR·push마다 정적 분석 + 테스트 |
| `ai_logs/<GitHub아이디>/YYYY-MM-DD-issue-N.md` + `TEMPLATE.md` | 사람별·이슈별 AI 사용 기록 |
| `prompts_log.md` | ai_logs를 모은 누적본 |
| `README.md` | 프로젝트 소개, 데이터 구조, 실행 절차 |

### 1.2 라벨 (4개 축)

- `type:` feature / bug / docs / setup / test
- `area:` 담당 영역 7개 (feed, compose, detail, interaction, firebase, ai, core)
- `priority:` high(다른 일을 막는 선행 작업) / medium(이번 마일스톤 안) / low(필수 끝난 뒤)
- `status: discussion` 구현 전 팀 결정 필요

### 1.3 마일스톤

과제 단계 = 마일스톤. `M0 · 초기 세팅` → `MP1` → `MP2` → `MP3` → `AI` → `최종 · 통합 검증·발표`.
각각 마감일이 있고, 설명에 **팀 내부 목표일**과 공식 제출일을 구분해서 적는다.

### 1.4 이슈

- 명세서를 기준으로 **처음에 이슈를 한꺼번에 다 만들어 둠** (10/31 하루에 31개). 전체 작업이 이슈 목록으로 보인다.
- 제목: `[단계] 할 일` 예) `[MP1] 글쓰기 입력·300자 제한·게시 상태·닫기 확인 구현`
- 본문 구조 (전부 동일):
  1. 한 줄 목표
  2. 화면 흐름 이미지 표 (이전 → 작업 → 이후)
  3. 메타: 담당(개발 N + 계정), **작업 기간(날짜 · 팀 내부 계획)**, **선행 이슈**, **관련 요구사항 ID**
  4. 구현 화면 Figma 링크
  5. 작업·완료 기준 체크리스트
  6. 검증 (테스트 케이스 번호)
  7. 명세서·일정 링크
- 마일스톤마다 마지막에 **검증·제출물 정리 이슈**가 하나씩 있음. 최종에는 회귀 검사, 재현 확인, 발표 준비.
- 결정용 이슈(#2): 안을 댓글로 올림 → 각자 "개발 N 담당하겠습니다" 댓글로 역할 확정 → 결정마다 날짜 붙인 댓글 → 마지막에 결정 요약 표.

### 1.5 일정 관리

3단: 마일스톤 마감일(큰 단위) / 이슈 본문 "작업 기간"(세부) / 노션 「전체 일정」(전체 그림).

### 1.6 브랜치·커밋·PR

| 대상 | 형식 | 예시 |
| --- | --- | --- |
| 브랜치 | `타입/#이슈번호-영어설명` | `feat/#7-feed-card` |
| 커밋 | `타입: 한글 명사형 제목` (50자 이내, 마침표 없음) | `feat: 피드 카드에 상대 시간 표시` |
| PR 제목 | `타입: #이슈번호 제목` | `feat: #40 JSON 기반 메모리 저장소 구현` |

- 타입: feat / fix / design / refactor / style / docs / test / chore
- PR 하나 = 이슈 하나, 본문에 `Closes #번호` (나눠야 하면 앞 PR은 `Refs #번호`)
- 변경 400줄 이내 권장, 작업 중이면 Draft PR
- 머지 조건: 리뷰 1명 승인 + CI 통과 + 충돌 없음 → **올린 사람이 직접 Squash and merge**, 브랜치 자동 삭제
- 리뷰: 해당 코드 줄에 「추가 / 삭제 / 변경」을 앞에 붙여 댓글, 고칠 게 정해지면 suggestion
- PR 리뷰 포인트에 "왜 이렇게 설계했는지"를 자세히 적음
- 하지 말 것: main 직접 push, force push, 비밀값·빌드 결과물 커밋, 이슈 없이 작업 시작
- 참고: 초반 PR은 브랜치 이름이 제각각이었고 규칙은 나중에 굳어짐 → 실버벨은 처음부터 맞춘다

### 1.7 AI 사용 기록

항목 ID `AI-YYYYMMDD-아이디-NN`. 요청마다 「프롬프트 한 줄 요약 / AI 응답 / 판단(채택·부분 채택·수정·거절 + 이유)」, 끝에 「직접 검증한 내용」.

## 2. 실버벨 적용안

### 2.1 저장소 파일

| 파일 | 실버벨 내용 |
| --- | --- |
| `README.md` | 게임 소개, 실행 방법(서버 먼저 → 클라 여러 개), 프로토콜 요약, 문제 파일 형식 |
| `CONTRIBUTING.md` | IntelliJ + JDK 버전, 다중 실행 설정법, 작업 흐름, 형식 규칙, 리뷰·머지, 주간 보고서 연결 |
| `.github/ISSUE_TEMPLATE/` | 기능·버그·작업 3종. config.yml에 노션 PRD·UI 명세서·주차별 일정 링크 |
| `.github/pull_request_template.md` | 미니피드 양식 + **주간 보고서 항목** (아래 2.6) |
| `.github/workflows/ci.yml` | Java 컴파일 + JUnit 테스트 (Gradle 기준) |
| `ai_logs/` + `TEMPLATE.md` | 그대로 가져감. 보고서 안내의 "AI 쓴 건 이해하고 보고서에 녹여라"와 맞음 |
| `questions/` | 문제 txt 파일 |

### 2.2 라벨

- `type:` feature / bug / docs / setup / test / design(UI 꾸미기)
- `area:` room(접속·대기실) / chat / question(문제·타이머·힌트) / bell / answer(답안·채점) / score / ui / core(공통 클래스·프로토콜)
- `priority:` high / medium / low (PRD 우선순위 상·중·하와 맞춤)
- `status: discussion`

GitHub 기본 라벨(bug, documentation 등)은 `type: bug` 등과 헷갈려서 지웠다(2026-11-09). 미니피드는 남겨 뒀다.
미니피드 라벨 설명은 영어였지만, 실버벨은 한국어로 쓰고 `area:` 설명에 PRD 기능 ID 그룹(A~H)을 붙였다.

### 2.3 마일스톤 (주차별)

미니피드처럼 단계 번호(M0~M5)로 부르고, 주간 보고서와 맞추려고 한 단계를 한 주(마지막만 2주)로 잡았다. 이름 괄호 안에 주차를 적는다.
날짜는 9주차 = 10/26 시작 가정. Q11 확인 후 고친다.

| 마일스톤 | 기간 | 내용 | 담당 |
| --- | --- | --- | --- |
| M0 · 기획·저장소 세팅 (10주차) | 11/2~11/8 | PRD·UI 명세서 확정, 저장소·규칙·CI·코드 뼈대 (미니피드 M0 역할) | 같이 |
| M1 · 접속·채팅과 핵심 로직 (11주차) | 11/9~11/15 | 같이: 수업 예제를 `net`으로 옮기기, A1~A2 접속·참가자 목록, B1~B2 채팅·시스템 메시지, 화면 전환 틀 / 각자: A `QuestionDeck`, B `BellQueue` (소켓 없이 JUnit) | 같이 + A / B |
| M2 · 한 문제 진행 (12주차) | 11/16~11/22 | A: C1~C3 문제 제시·타이머·다음 문제, F1~F2 점수·점수판 / B: D1·D3 벨·순서 표시, E1~E3 답안·채점·판정 → **한 문제가 끝까지 돈다** | A / B |
| M3 · 한 판 완성 (13주차) | 11/23~11/29 | A: C4 초성 힌트, A3·F3 준비·시작·최종 순위 / B: D4~D6 답변 시간·다음 차례·재도전 금지, G1~G2 퇴장·끊김 → **필수 기능 끝** | A / B |
| M4 · 부가 기능·UI (14주차) | 11/30~12/6 | B3~B4 정답 가리기·명령어, 선택 기능(H3·H1·H5·H7 우선), UI 꾸미기. 밀린 필수 기능이 있으면 먼저 | 나눠서 |
| M5 · 검증·발표 (15~16주차) | 12/7~12/20 | N1~N11 검증, 시간 임시값 확정, 버그 수정, 시연 영상, 발표 자료 | 같이 |

**일정 원칙**: 코딩은 11주차부터 바로 시작하고, 필수 기능(A~G)은 **13주차까지** 끝낸다. 14주차는 부가 기능·UI, 15~16주차는 검증과 여유분이다.
대신 한 주에 몰아서 하지 않게, 한 사람당 한 주에 이슈 3~4개로 나누고, 상대가 기다리는 기능은 메서드 이름만 먼저 작은 PR로 올린다.
11주차부터 소켓과 상관없는 핵심 로직(`QuestionDeck`, `BellQueue`)을 각자 먼저 만들어 두면, 12주차에는 네트워크로 연결만 하면 된다.

마일스톤마다 마지막에 **주차 통합 테스트 이슈** 하나 (미니피드의 검증·제출물 이슈 역할).

**이슈 크기 원칙**: 미니피드처럼 목적 하나당 이슈 하나로 나누고, 담당은 반드시 한 명. 서로 상관없는 기능은 묶지 않는다.
이슈 하나 = 주간 보고서에서 "동작 흐름 → 핵심 코드 → 테스트 결과 → 문제 해결"을 한 덩어리로 설명할 수 있는 단위.
예) `[M2] 벨 대기열과 순서 표시 (D1~D3)` 하나로 서버 `BellQueue` + 클라 벨 버튼·순서 표시까지.
전체 이슈는 35개(M0 2, M1 8, M2 7, M3 6, M4 9, M5 3). 한 사람 기준 주당 3~4개이고, 마일스톤 끝 통합 테스트는 같이 한다.

### 2.4 역할 (PRD Q10)

모든 이슈에 담당은 한 명(한 라인)이다. 같이 하는 건 마일스톤 끝 통합 테스트뿐이고, 거기도 진행·기록 담당을 정한다.

- 라인 A · 대기실·채팅·문제·점수: A2·A3, B1~B3, C1~C4, F1~F3, H1·H7, 문제 파일 취합, 게임 화면의 문제·힌트·시간·점수판·채팅 영역
- 라인 B · 접속·구조·벨·답·예외: A1(수업 예제 이식), 메시지 처리 구조, 게임 화면 틀, D1~D6, E1~E3, G1·G2, B4, H3·H5, 게임 화면의 벨·순서·답 입력 영역 (소켓·스레드 비중이 커서 그쪽에 더 자신 있는 사람)
- 라인 경계: 문제 타이머의 일시정지·재개와 점수 규칙(감점 포함)은 라인 A가 만들고, 라인 B는 호출만 한다
- 여유 기능(H2·H4·H6·H8·H9)은 M4 통합 테스트에서 할지 정하고 그때 이슈를 만든다
- 문제 파일은 반씩 작성
- 누가 어느 라인인지는 결정 이슈에 댓글로 확정 (미니피드 #2 방식)

### 2.5 이슈 양식

등록한 35개 이슈와 `.github/ISSUE_TEMPLATE/feature.yml`이 같은 구조다.

```
제목: [M2] 벨 누르기·순서 표시와 게임 화면 키 조작

(한 줄 목표)

- 담당: 라인 B
- 작업 기간: 2026/11/16~11/19 · 팀 내부 계획
- 선행 이슈: #7, #9, #11
- 관련 요구사항: D1 벨 누르기·D3 순서 표시·B1 채팅

## 구현 위치 (참고)
- 어느 클래스·패키지에 둘지. 방법은 담당자가 정한다

## 작업·완료 기준
아래를 모두 체크하고, PR이 리뷰 승인·CI 통과로 머지되면 닫는다.
- [ ] 확인할 수 있는 단위로 (숫자·횟수·화면 문구까지)

## 검증
- JUnit / 서버 1 + 클라이언트 N개 / PRD 시나리오 5.x / 콘솔 클라이언트
```

### 2.6 PR 양식 (주간 보고서 연결)

```
## 관련 이슈
Closes #

## 작업 내용 (보고서 2)
## 동작 흐름 · 알고리즘 (보고서 3)
## 핵심 코드 설명 — 왜 이렇게 했는지 (보고서 4)
## 검증 결과 — 컴파일 / JUnit / 실행 화면·서버 로그 (보고서 4)
## 막혔던 점: 현상 → 원인 → 시도 → 결과 (보고서 5)
## AI 사용 기록 (ai_logs 링크 또는 미사용)
## 리뷰 포인트
## 체크리스트
```

주간 보고서는 그 주 마일스톤의 내 PR들을 모아 옮기면 된다.

| 보고서 항목 | GitHub에서 가져올 곳 |
| --- | --- |
| 2. 담당 내용 | 그 주에 닫은 내 이슈·PR |
| 3. 동작 흐름 | PR 「동작 흐름」 |
| 4. 핵심 코드·결과 | PR 변경 코드 + 실행 화면·로그 |
| 5. 문제 해결 | PR 「막혔던 점」 + 이슈 댓글 |
| 6. 남은 문제·계획 | 열린 이슈, 다음 주 마일스톤 |
| 프로젝트 폴더 압축 | 주말에 `git tag week11` → GitHub 태그 페이지에서 ZIP |

보고서는 개인 제출이라 각자 자기 라인 이슈·PR 위주로 쓴다.

### 2.7 브랜치·커밋·PR 규칙

미니피드 형식 그대로. 2명이라 리뷰어는 항상 상대방 1명.

- 둘 다 쓰는 파일(`MessageType`, `GameConfig`, 핸들러 등록부)을 고칠 때는 그것만 담은 작은 PR로 먼저 머지
- `GameRoom`은 라인 A 소유. 라인 B는 작은 PR + 라인 A 리뷰
- 새 메시지는 서버·클라이언트 모두 종류별 처리 클래스를 등록해서 추가한다(큰 `switch`에 `case` 추가 금지)
- 메시지 형식은 보내는 이슈의 담당이 정하고 `MessageType` 주석·PRD 9절을 같이 고친다
- 작업 시작 전 항상 main pull, PR은 작게 자주

### 2.8 테스트

- 단위 테스트(JUnit): 소켓과 분리한 로직 클래스 — `QuestionDeck`(#8), `BellQueue`(#9), `ScoreBoard`(#12), 채점기(#15), `HintMaker`(#18). 게임 규칙은 테스트용 가짜 `Broadcaster`로
- 통합 테스트: 마일스톤 끝(#10·#17·#23·#32), 서버 1 + 클라 3개로 PRD 5절 시나리오를 구현된 데까지 따라 하기. 찾은 문제는 `type: bug` 이슈로
- 서버를 속이는 메시지(차례 아닌 `ANSWER`, 가짜 `SCORE`)는 콘솔 클라이언트(#4)로 직접 보내 확인
- 서버가 주고받는 메시지를 시각과 함께 콘솔에 찍어두기 (보고서 4번 자료)
- 15~16주차: PRD 7절 N1~N11 측정 방법·통과 기준대로

### 2.9 설계 원칙 · 코드 품질

설계는 소프트웨어공학 **SOLID 원칙(SRP·OCP·LSP·ISP·DIP)을 준수한다.** 어떻게 지켰는지는 각자 PR과 주간 보고서에 설명한다.

**패키지 구조**

```
common/          서버·클라 공용
  MessageType    메시지 종류 enum (JOIN, BUZZ, HINT ...)
  Message        한 줄 문자열 ↔ 객체 변환 (자르기 규칙 한 곳에)
server/
  net/           소켓 입출력만 (ClientHandler, ServerMain)
  game/          게임 규칙만, 소켓 모름 (GameRoom, BellQueue, ScoreBoard, QuestionDeck, HintMaker)
  game/answer/   AnswerChecker 인터페이스 + MultipleChoiceChecker, ShortAnswerChecker
  handler/       메시지 종류별 처리 클래스 (BuzzHandler, AnswerHandler ...)
client/
  net/           ServerConnection (보내기·받기)
  ui/            화면 (TitleScreen, LobbyScreen, GameScreen, ResultScreen)
```

**코드 규칙**
- 매직 넘버 금지: 시간(20초·10초·힌트 시점), 최대 인원, 점수는 `GameConfig` 상수 한 곳에
- 공유 상태(`GameRoom`, `BellQueue`)는 메서드로만 접근, 동기화는 그 클래스 안에서만
- 클래스·메서드 이름은 PRD 용어 그대로 (벨 대기열 → `BellQueue`)
- 공개 메서드에 Javadoc 한두 줄 (무엇을, 어떤 조건에서)
- 로직 클래스는 JUnit 테스트 필수, 테스트 이름은 "~하면 ~된다"

**과설계 주의**: 2명·몇 주짜리 과제다. 이유를 설명할 수 없는 구조는 넣지 않는다. 뼈대 단계에서 구조를 같이 정하고, 이후엔 이 틀 안에서만 작업한다.
