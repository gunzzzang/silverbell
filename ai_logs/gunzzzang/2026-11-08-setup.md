- AI 응답: 라벨 4축, 단계별 마일스톤, 이슈 본문 구조, 브랜치·커밋·PR 형식, AI 기록 방식을 정리하고 `docs/github-plan.md`로 작성
- 판단: 수정. 미니피드는 4명이라 이슈를 31개로 잘게 나눴지만, 실버벨은 2명이고 주간 보고서에서 설명할 수 있어야 해서 **한 주에 한 사람 1~2개**로 줄였다. 마일스톤도 단계별 대신 주차별로 바꿨다.

### 2. 규칙 파일

- 프롬프트: 계획대로 README, CONTRIBUTING, 이슈·PR 템플릿, CI 작성 요청
- AI 응답: 미니피드 형식을 IntelliJ·Gradle·Java 기준으로 바꾸고, PR 템플릿 항목에 주간 보고서 번호(보고서 2~5)를 붙임
- 판단: 채택. PR만 잘 쓰면 보고서로 옮길 수 있게 하는 게 목적이다.

### 3. 코드 뼈대

- 프롬프트: 재사용성 높게, 소프트웨어공학 원칙에 맞는 패키지 구조로 뼈대 요청
- AI 응답: `common`(메시지·설정) / `server.net`(소켓) / `server.game`(규칙) / `server.handler`(메시지별 처리) / `client.net` / `client.ui`로 나누고, `Broadcaster`(DIP), `MessageDispatcher`(OCP), `AnswerChecker`(Strategy), `MessageListener`(Observer) 인터페이스를 둠. `Message`·`MessageDispatcher`만 구현하고 나머지는 할 일을 적은 빈 클래스로 둠
- 판단: 부분 채택. 접속·채팅·게임 규칙은 11주차부터 직접 구현해야 보고서에 쓸 수 있으므로 비워 두었다. 패턴은 이유를 설명할 수 있는 5개로만 제한했다.

### 이해한 내용

- `Message.values(count)`는 `split(";", count)`라서 마지막 값이 나머지 전부를 가진다. 그래서 채팅 글에 `;`가 있어도 깨지지 않는다.
- `MessageDispatcher`에 등록하지 않은 종류(예: 클라이언트가 보낸 `SCORE`)는 처리되지 않으므로, 가짜 점수 메시지를 따로 막는 코드가 없어도 무시된다(PRD N7).

### 직접 검증한 내용·결과

- `javac --release 17`로 main 코드 컴파일 성공
- `Message`·`MessageDispatcher` 테스트와 같은 내용을 JUnit 없이 직접 실행해 11개 확인 통과
- JUnit 테스트(`./gradlew test`)는 세팅 환경에서 JUnit을 받을 수 없어 미실행 → GitHub CI 첫 실행에서 확인
- IntelliJ에서 `ClientMain` 창이 뜨는지 미확인 (다음 확인 항목)
