### 2. 서버: 벨 받기를 `GameRoom` 잠금 안에서

- 프롬프트: `BUZZ` 핸들러가 `isRoundActive()`로 확인하고 `BellQueue`에 넣으면 되는지
- AI 응답: 확인(`isRoundActive`)과 넣기·전송을 따로 하면 그 사이에 `finishRound()`가 끼어들어 `REVEAL` 뒤에 `QUEUE`·`TURN`이 갈 수 있음. 그러면 문제 영역(#11)이 `TURN`을 받고 끝난 문제의 시간 바를 다시 움직임. 그래서 `GameRoom.buzz()` 하나에서 잠근 채로 확인·줄 넣기·전송을 하고, `BuzzHandler`는 `StartHandler`처럼 한 줄로 넘기기만 함
- 판단: 채택. `QUESTION`·`REVEAL`도 `GameRoom`이 잠근 채 보내고 있어 같은 방식.

### 3. 서버: 벨을 울린 순간의 힌트 수

- 프롬프트: 이슈 「벨을 울린 순간 공개돼 있던 힌트 수를 같이 기록」을 어디에 둘지
- AI 응답: `BellQueue.add(닉네임, 힌트 수)`로 줄에 넣을 때 같이 기록하고 `hintCountOf(닉네임)`으로 꺼냄. `reset()` 때 같이 비움. 연타로 무시된 벨은 처음 값을 바꾸지 않음
- 판단: 채택. 「줄에 선 순간」과 「힌트 수 기록」이 같은 때라 한 메서드로 묶음(따로 두면 둘 사이에 힌트가 공개될 수 있음). `add(닉네임)`을 남겨 두는 대신 인자를 바꿔 기존 테스트도 고침.

### 4. 메시지 형식

- `QUEUE|주성;이건;민수` 줄 순서, 맨 앞이 지금 차례. 줄이 비면 `QUEUE|`
- `TURN|주성;10000` 지금 차례인 사람;답변 시간(ms). 차례 없음은 `TURN|` (#11 문제 영역이 이미 빈 값으로 처리함)
- `TURN`은 빈 줄에 처음 들어왔을 때만 보냄. 두 번째 사람부터는 차례가 그대로라 `QUEUE`만
- 벨을 울리면 UI 명세서 M5대로 `SYSTEM|주성 님이 벨을 울렸어요!`
- 판단: 채택. `MessageType` 주석과 PRD 9절에 같이 적음.

### 5. 화면: 보내는 방법 — `MessageSender`

- 프롬프트: 게임 화면 영역(벨·채팅 입력칸)이 서버로 보내려면?
- AI 응답: 게임 화면은 접속 전에 만들어져서 연결을 직접 들 수 없음. 대기실은 `Consumer<Message>`를 받지만 CLAUDE.md 3-5절이 `java.util.function`을 쓰지 말고 `MessageListener`처럼 우리 인터페이스를 만들라고 함 → `client/net/MessageSender` 인터페이스를 만들고 `MainFrame`이 익명 클래스로 넘김
- 판단: 채택. CLAUDE.md 5절 표의 「`interface`로 의존 끊기」 줄에 추가.

### 6. 화면: 스페이스바 = 벨 / 채팅 입력칸

- AI 응답: #7에서 만든 포커스 구조를 그대로 씀. 채팅 입력칸(`ChatPanel`, 라인 A)은 이슈대로 열기·닫기 부분만 추가. 열면 입력칸이 포커스를 가져가 스페이스바가 글자가 되고, Enter로 보내면 닫히면서 `GameScreen.takeKeyFocus()`로 돌려받음. 빈 칸에서 Enter는 그냥 닫기. 막 보이게 된 입력칸은 포커스 요청이 실패할 수 있어 수업 `FocusAdapterExample`처럼 `invokeLater`
- 판단: 채택. `ChatPanel`은 생성자에 `MessageSender`와 `GameScreen`을 받도록 바뀜(수업 ex2 「생성자로 전달」 방식). 채팅 표시(CHAT·SYSTEM 받아서 보여주기)는 라인 A 범위라 손대지 않음.
- 벨 순서 영역 글자는 처음에 `StringBuilder`로 만들었다가 CLAUDE.md 3-7절(문자열은 기본 메서드)에 맞게 수업 채팅창처럼 `textArea.append`로 바꿈.

### 이해한 내용

- `synchronized` 메서드 안에서 다른 객체(`BellQueue`)의 `synchronized` 메서드를 부르는 건 괜찮음. 잠금 순서가 항상 `GameRoom` → `BellQueue` 한 방향이라 서로 기다리는 일이 없음(#11 리뷰의 데드락은 두 방향이었음).
- 「확인하고 행동하기」를 두 번의 잠금으로 나누면 그 사이에 상태가 바뀔 수 있다. 벨 대기열(#9)에서 배운 것과 같은 문제가 메시지 순서(REVEAL 뒤의 TURN)로 나타난 것.
- 키 이벤트는 포커스를 가진 컴포넌트에만 간다. 그래서 「입력칸이 열려 있으면 벨 무시」 같은 조건문 없이 포커스만 옮겨서 스페이스바의 뜻이 바뀐다.
